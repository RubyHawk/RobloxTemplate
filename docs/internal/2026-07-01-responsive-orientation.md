## Findings

A user-supplied guide recommended `Camera.ViewportSize` as the primary responsive signal, `PlayerGui.CurrentScreenOrientation` for landscape-flip detection, and setting `StarterGui.ScreenOrientation` for rotation support. All of the referenced properties and enum values (`LandscapeLeft`, `LandscapeRight`, `LandscapeSensor`, `Portrait`, `Sensor`) checked out against the current class/enum reference. Two things the guide didn't call out:

- `StarterGui.ScreenOrientation` **already defaults to `Sensor`** — this repo never overrides it, so portrait/landscape rotation is already permitted today. Set it explicitly anyway so the intent survives an engine default change and isn't just an accident of never having touched the property.
- `GuiService.ViewportDisplaySize` only distinguishes `Small` (tablet/mobile/handheld), `Medium` (laptop/monitor), `Large` (TV or bigger) — it cannot tell a phone from a tablet. `Camera.ViewportSize` (actual pixel/offset dimensions) has to be the real signal for that distinction, exactly as the guide itself argued.

The guide's example script targets a different, hypothetical game (`Workspace.CurrencyPlatform`, a `BillboardGui` named `UpgradeBubble`, panels named `CurrencyPanel`/`UpgradePanel`) that doesn't exist in this template. Adapted the *approach* (viewport-size-driven, orientation as a supporting signal, never gameplay-authoritative) to this template's real structure instead of porting the example verbatim:

- The authored screens (`InventoryScreen`, `StoreScreen`, etc.) and `Navigation` already carry `UISizeConstraint` Min/MaxSize pairs (screens: 300×300 to 560×620; nav: 74×320 to 92×450) — the template already guards against screens ballooning on a tablet/desktop-sized viewport or collapsing on a small phone. No need to duplicate that.
- `AudioController`-style controllers already exist under `src/client/Controllers/`; `ResponsiveController` follows the same pattern rather than inventing a new module shape.
- The existing per-player `uiScale` setting (`Settings` screen, 0.8–1.2, saved server-side) already drives `Root.InterfaceScale.Scale`. The new automatic device-based factor multiplies with that value rather than fighting or replacing a player's explicit preference.
- Did not build the guide's 7-way profile taxonomy (`PhonePortrait`/`PhoneLandscape`/`TabletPortrait`/`TabletLandscape`/`DesktopNarrow`/`DesktopWide`/`ConsoleLarge`) — nothing in this template's screens currently branches into that many distinct layouts (no side-panel/dashboard mode exists), so it would be unused abstraction. Exposed just what's actually consumed: orientation, raw viewport size, and an input-capability flag, as attributes on `Root`.
- Orientation/viewport data stays a client-only display concern, per the guide's own correct point — nothing server-authoritative (currency, rewards, purchases) reads any of it.

## Follow-up: device/orientation coverage verification — 2026-07-01

The original `ResponsiveController` only ever did viewport/orientation *detection* plus a single modest scale multiplier (0.94–1.06) — it never built distinct layouts per device or orientation, and had not been visually verified past phone-portrait width. Rendered the real, committed `TemplateUI.model.json` (not a mockup) at five configurations — phone portrait 375×812, phone landscape 812×375, tablet portrait 768×1024, tablet landscape 1024×768, laptop 1440×900 — for both the idle Home state and an open screen (Store), using a mechanical HTML renderer that computes real UDim2/AnchorPoint/UISizeConstraint pixel boxes from the authored file. Found two real, confirmed bugs (not renderer artifacts — cross-checked against `AbsolutePosition`/`AbsoluteSize`-equivalent math and `ZIndex` paint order):

1. **Navigation rail overflow in landscape phone.** `Navigation` is authored as a fixed 82×390 offset rail (its `Size` Scale component is 0, so it never adapts to viewport height on its own); its existing `UISizeConstraint` (74×320–92×450) was inert since 390 already sits inside that range. On a ~375-tall landscape phone the fixed 390 exceeds the viewport, so the rail overflowed flush against both the top and bottom edges with zero margin.
2. **HUD/modal overlap on short viewports.** `CurrencyHUD` sits at a fixed pixel position (y 18–110) and stays visible while a screen is open; `Screens` has `ZIndex 40` vs `CurrencyHUD`'s `ZIndex 5`, so an open screen always paints over the HUD wherever they overlap. Every modal (`StoreScreen`, `InventoryScreen`, `MoreMenu`, `ScreenTemplate`, etc. — all ten screens under `Screens` plus the two siblings share the identical `AnchorPoint [0.5, 0.5]` + `UISizeConstraint` pattern) is vertically centered via a Scale-based Position with only a static Max-height clamp, with no awareness of the HUD's real position. Confirmed the resulting overlap at phone-portrait (812), phone-landscape (375), and tablet-landscape (768).

Fixed both in `ResponsiveController.luau` by tightening (never loosening past the authored default) each affected instance's existing `UISizeConstraint.MaxSize` live, computed from real anchor-point geometry so the fix is exact rather than assuming symmetric centering:

- Verified via a DevForum engine-bug report (`UIScale does not respect UISizeConstraint properties`, Nov 2022, Roblox staff-acknowledged, unresolved/backlog) that `UISizeConstraint.MinSize`/`MaxSize` are evaluated in *pre-UIScale* units while `UIScale` multiplies the final `AbsoluteSize` afterward without re-clamping — exactly this codebase's architecture (one `UIScale` on `Root` scaling a subtree of separately-`UISizeConstraint`-ed descendants). The fix computes safe limits in real on-screen pixels (via the anchor-point identity `AbsolutePosition + AnchorPoint*AbsoluteSize = size-invariant anchor reference point`, stable across repeated resize events) and divides by the current `UIScale.Scale` before writing back into `MaxSize`, so it stays correct at every device-scale tier.
- Caches each instance's original authored `MaxSize` on first use and always recomputes from that original, so the clamp fully restores (not ratchets down) the moment there's room again — e.g., rotating a landscape phone back to portrait.
- Nav rail's Position Y-scale (0.48, not a true 0.5) meant a naive "viewport height minus 2×margin" bound gave an asymmetric ~8.5px/23.5px split instead of the intended 16px on both edges; solved each edge's constraint separately from the anchor point instead of assuming symmetric centering. Verified 16px exactly by pixel-sampling the rendered output.

**Residual, honestly-reported limitation:** at the most extreme case tested (phone landscape, ~375px tall), the HUD/modal overlap is *reduced but not eliminated* (measured 88px of HUD covered before the fix vs. 84px after, by pixel-sampling where the screen's red header begins). This is a hard geometric conflict, not a bug in the fix: the modal's pre-existing `MinSize` floor (300px tall) plus the HUD's fixed 110px-tall reserved area plus a minimal gap exceeds the available 375px viewport height (300 + 120 > 375) — no repositioning or resizing within the existing `MinSize` floor can satisfy both constraints simultaneously at this height. Resolving this fully would require loosening the pre-existing `MinSize` floor (risks an illegibly small modal) or hiding/collapsing the HUD while a screen is open (a bigger UX behavior change, and one that would look inconsistent with the bright/icon-driven reference games, which typically keep the currency readout visible even with a shop open) — both are judgment calls left for a follow-up decision rather than made unilaterally here.

Separately, found and fixed a pre-existing (not introduced by this session's earlier restyle passes) narrow-width-specific layout bug while doing this verification: `StoreScreen/Content/StoreHeader` was a fixed 60px-tall Frame, but its own `Body` label was already authored with a 44px-tall box positioned 48px down (needs 92px total) — comfortably fits at tablet/laptop widths where the description stays on one line, but at phone modal widths (~300–340px) the sentence wraps to two lines and the second line visibly spilled out past the header's own yellow background. Confirmed via `LayoutOrder`/`Size` inspection that this pattern exists exactly once in the real screen (a second match is the licensed `ShowcaseCanvas` duplicate at `ZIndex 192`, intentionally left untouched, consistent with every other restyle pass in this repo). Fixed by growing the header to 100px and shifting `ProductsGrid`'s position and the scroll `CanvasSize` down/taller by the same 40px delta (`scripts/fix_store_header_overflow.py`).

**Bottom line on device/orientation coverage:** viewport-size and orientation *detection* work identically on any device (phone, tablet, laptop, desktop) since they read `Camera.ViewportSize` directly. What's now built and verified is a single shared layout (not a distinct per-device or per-orientation redesign) that auto-scales modestly and defends its edges — nav rail and modal screens — against overflow/overlap using the pre-existing `UISizeConstraint` values as the ultimate floor/ceiling, verified by rendering the actual committed file at all five sizes rather than assumed from reading the code.
